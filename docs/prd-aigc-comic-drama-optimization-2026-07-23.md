## 1. 产品目标（3 个正交目标）

**目标 A：流程可控性 — 消灭"等待黑洞"**
让 8 阶段×60 集的长流程变得透明、可持久化、可中断恢复、可实时追踪。用户不再被迫守在屏幕前做无效等待，关闭页面不等于静默失败。
（来源：用户研究 P0#1/2/3 + 数据分析架构瓶颈#1/2 + 指标 M3/M6）

**目标 B：产出质量 — 从"一次性"到"可精修可复用"**
提升 AI 生成结果的角色一致性与可迭代性，建立角色资产体系，支持局部精修，使产出从"草稿级"进化为"可发布级"。
（来源：竞品分析#1 + 用户研究 P1#5/P2#7 + 数据分析 M4）

**目标 C：规模效率 — 60 集批量从 25 小时到 8 小时**
通过视频批量并行、API 速率控制、自动化审核和成本管控，将单集生产耗时从 35-50 分钟压缩至 ≤30 分钟，60 集批量从 15-25 小时压缩至 ≤8 小时。
（来源：数据分析效率量化 + 数据分析#2/5 + 竞品 Agent 化 + 指标 M1/M5/M7）

## 2. 用户故事（5 个场景）

**US-1**：作为漫剧创作者，我希望启动 60 集批量生产后可以关闭浏览器离开，稍后回来时看到所有任务的状态（完成/失败/进行中），失败的可以一键重试——这样我不必守在屏幕前做无效等待。

**US-2**：作为漫剧创作者，我希望在项目首页看到一个看板，60 集×8 阶段的状态一目了然——这样我在长流程中随时知道"做到哪了"，不会迷失方向。

**US-3**：作为漫剧创作者，我希望能选中某个分镜或剧本段落，单独让 AI 重新生成而不是整集重来——这样我可以快速精修不满意的细节。

**US-4**：作为漫剧创作者，我希望视频生成结果以网格展示，满意的批量通过、不满意的批量重做——这样 720 次逐个确认的噩梦不再发生。

**US-5**：作为漫剧创作者，我希望角色图片生成后能在全 60 集中保持一致，系统自动检测一致性不达标的图片——这样我的漫剧观感统一，不用手动排查。

## 3. 用户研究洞察（来自瑞思）

### 核心发现
工具最大的体验瓶颈不在功能缺失，而在"长流程中的等待黑洞与状态失控"——8 阶段×60 集的规模下，用户面临"反复经历等待→中断→迷失→重做"的循环。

### 用户画像
- **核心用户**：独立 AIGC 创作者 / 小型工作室（1-3 人），技术能力中等，日活 2-4 小时
- **动机**：副业变现 / 内容创业 / 技术探索
- **关键诉求**：效率 > 质量 > 成本 > 控制

### 用户旅程地图（情绪曲线：双谷一峰）
起点（大纲生成）：兴奋 → 剧本生成：满意（峰）→ 分镜+视频生成：焦虑（谷）→ 字幕+导出：疲惫（谷）→ 发布：释然

### 核心痛点（8 个，按严重程度）

| 级别 | 痛点 | 描述 |
|------|------|------|
| P0 | 工作流断裂 | 页面刷新模式导致阶段间上下文断裂，用户在 8 阶段长流程中频繁迷失 |
| P0 | 状态丢失 | 长任务期间页面关闭=静默失败，daemon 线程可能继续但用户无法获知结果 |
| P0 | 等待黑洞 | 无进度预估、无完成通知、必须主动盯盘，被迫"守在屏幕前"做无效等待 |
| P1 | 创作控制力不足 | 固定 60 集+6 种题材，AI 生成结果"一次性产出"，缺乏迭代精修能力 |
| P1 | 错误恢复困难 | 生成失败后无清晰恢复路径，无自动重试、无批量重试 |
| P2 | 批量操作效率低 | 720-1200 次视频生成逐个确认不可持续 |
| P2 | 无资产复用 | 无资产复用机制，每集从零开始 |

## 5. 数据依据（来自数析）

### 7 个核心指标定义

| 编号 | 指标 | 当前值 | 目标值 |
|------|------|--------|--------|
| M1 | 单集生产耗时 | 35-50 min | ≤30 min |
| M2 | 视频生成成功率 | 未量化 | ≥92% |
| M3 | 任务中断恢复率 | 0%（无恢复机制） | ≥95% |
| M4 | 角色一致性评分 | 未量化 | ≥0.75 |
| M5 | 单集人工干预次数 | 未量化 | ≤3 次 |
| M6 | 全流程完成率 | 未量化 | ≥80% |
| M7 | 单集 API 成本 | 未量化 | ≤¥15 |

### 5 大架构瓶颈

1. **线程模型不可靠**（最高风险）：daemon Thread 无重试、无持久化、进程重启 100% 丢失任务
2. **轮询式前端效率极低**：60 集并行 10 任务时每分钟 200 次纯轮询请求
3. **本地文件存储**：60 集约 2-5GB 成片+多版本可达 10-20GB，无法水平扩展
4. **无统一速率限制器**：多任务可能同时打满 API 配额导致 429
5. **无监控/指标看板**：无运行时指标采集，无法量化瓶颈

### 效率瓶颈量化

- 单集生产：35-50 分钟（视频生成占 70-85%）
- 60 集批量：15-25 小时（现实预期含人工干预）
- 人工干预占总时间 15-30%

## 7. 关键流程图 / UI 设计稿

### 优化后理想工作流（文字描述）

```
项目首页（总览看板：60集×8阶段状态矩阵）
  │
  ├─ 大纲生成 ──→ 6 候选选择 ──→ 自动进入剧本
  │                                  │
  ├─ 剧本生成 ──→ 60 集剧本 ──→ 局部重写（可选）
  │                                  │
  ├─ 角色设定 ──→ 角色图片 ──→ 一致性检测（CLIP）
  │                                  │
  ├─ 分镜生成 ──→ 12-20 个/集 ──→ 批量审核（网格预览）
  │                                  │
  ├─ 视频生成 ──→ 并行生成 ──→ 实时进度条 + 预估时间
  │                                  │
  ├─ 字幕对齐 ──→ ASR + 手动修正
  │                                  │
  ├─ 成片导出 ──→ FFmpeg 拼接 ──→ 批量导出
  │                                  │
  └─ B 站发布 ──→ 数据回流面板
```

### 关键 UI 变化

1. **项目总览看板**：60 集作为行，8 阶段作为列，每格显示状态色块（灰=待开始、蓝=进行中、绿=完成、红=失败），点击跳转到对应阶段
2. **实时进度面板**：右侧固定栏，显示当前任务进度条、预估剩余时间、任务队列
3. **批量审核视图**：网格布局展示生成结果，支持多选+批量标记
4. **角色一致性面板**：角色参考图 + 一致性评分 + 低一致性预警标记

## 8. Non-goals（明确不做什么）

1. **不做多用户协作** — 当前保持单用户架构，团队协同编辑不在 v1 范围
2. **不做 SaaS 化/商业化** — 暂不引入订阅制、计费体系、多租户
3. **不做移动端适配** — 聚焦桌面 Web 体验优化
4. **不做自研模型训练** — 继续依赖外部 LLM/图片/视频 API
5. **不做实时协同编辑** — 非 Google Docs 式多人同时编辑
6. **不做全新工作流引擎** — 不替换 8 阶段主流程结构，仅优化各阶段内体验

### 优先级排序逻辑：止血 → 提速 → 增强 → 竞争

- **Q1 止血优先**：daemon Thread 不可靠是根因性缺陷，在根基不稳时推进效率优化等于在沙地上建楼
- **Q2 提速紧随**：视频生成占 60-70% 时间，效率提升带来最直接的用户感知
- **Q3 增强在后**：角色一致性是核心差异化技术，但 Confidence 低、Effort 高，需先解决确定性问题
- **Q4 竞争为长期**：Agent 架构和多用户改造是高 Effort 低 Confidence 大工程，不紧急但重要

### 依赖关系

```
Q1: 任务持久化(Celery) ──→ 错误恢复/重试 ──→ WebSocket ──→ 监控看板
                                │
Q2:                    并行视频生成 ──→ 批量操作框架
                       资产库系统 ──→ (后台并行) 对象存储迁移
                                │
Q3:                    角色一致性引擎(需资产库基础)
                       细粒度编辑(需资产引用关系)
                       预览迭代(需版本管理+错误恢复)
                                │
Q4:                    Agent 架构迁移(需 Q1-Q3 稳定基础)
                       多平台发布(需 Q3 API 调研)
```

### 利益相关者沟通要点

**高管版**：用 4 个季度完成从"可靠工具"到"竞争平台"的升级，预期单集制作效率提升 50%+，发布渠道扩展到 4+ 平台。关键决策点：Q2 确认 API 并发配额、Q3 确定角色一致性技术路线、Q4 确认 Agent 架构投入节奏。

**工程版**：Q1 替换线程模型为 Celery+Redis 并引入 WebSocket，这是后续所有并行/批量能力的架构基础。最大技术风险：Q2 外部 API 速率限制（需 Q1 末 Spike）、Q3 角色一致性技术路线（需 Q2 启动预研）。

**设计版**：体验从"被动等待"到"实时感知"，从"逐个操作"到"批量管理"，从"一键生成"到"精细可控"。Q1 的状态可视化和 Q3 的编辑交互是两个设计投入最大的节点，建议提前 2 周开始设计探索。
